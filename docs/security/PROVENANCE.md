# IZWI signed provenance (not C2PA)

Every new render has a sibling `<render.mp4>.provenance.json` sidecar. It contains a versioned envelope (`v: 1`, `kind: izwi-signed-provenance`) with the MP4 SHA-256, output and project IDs, creation time, creator declaration ID/time/text, transcription and planner labels, generic consent labels with ledger sequence and entry hash, and a key ID. It contains no guest names. Its Ed25519 signature covers the canonical envelope serialization used by `src/server/ledger.ts`.

The signer is the Ed25519 private key derived by `ledgerKeys()` from the server's `IZWI_MASTER_KEY`. The sidecar records the first 16 hex characters of the SHA-256 of the public key hex string. This is a self-held IZWI key, not a public certificate authority. A verifier must obtain the trusted public key independently; the key ID alone does not establish trust. Rotating `IZWI_MASTER_KEY` changes this signing key.

The signature proves that the holder of the matching private key signed those exact envelope fields and that the referenced MP4 bytes match the signed SHA-256. The consent sequence/hash references make a record auditable against the IZWI consent ledger. They do not prove who answered, that consent was informed, that a declaration is true, that the media is authentic or unaltered before IZWI received it, or that an external platform accepted it. The signature does not prove ownership, legal permission, translation accuracy, or public trust. This is **IZWI signed provenance (not C2PA)**.

Release order: render to a temporary file; build and locally verify the signed sidecar; inside one database transaction re-read the declaration and each relevant person's current consent ledger entry and require the exact snapshotted declaration ID/time and consent ID/sequence/hash; retain the existing lease and rights checks; then move the files into place, register the MP4 asset, and mark the output ready. A mismatch discards temporary and final render files and leaves a failure note. Render packages include each sidecar beside its MP4.

## C2PA spike (2026-11-26)

**Failed; C2PA was not added.** `npm view @contentauth/c2pa-node version license os cpu` reported latest `0.12.2`, MIT, and no `os` or `cpu` metadata. The [current upstream README](https://github.com/contentauth/c2pa-js/blob/main/packages/c2pa-node/README.md) states: “This command will download precompiled binaries for the following systems:” and lists Linux x86_64/aarch64, macOS aarch64/x86_64, Windows x86, and Windows ARM. This Windows 11 / Node `v24.18.0` environment is Windows x64; no x64 prebuilt is listed, and the package's install fallback did not produce a usable native binary. The latest package's current signing API is `Builder.newAsync()` and `builder.sign(signer, inputAsset, outputAsset)` (same README). The exact spike version was `0.12.2`; the dependency was removed after the platform check, and no test certificate or C2PA claim was created.

The CLI `npx tsx scripts/verify-provenance.ts <render.mp4>` verifies the adjacent sidecar using the current ledger key derived from local server configuration. To independently verify with a different trusted key, call exported `verifyProvenance(json, mp4Bytes, trustedPubHex)`.
